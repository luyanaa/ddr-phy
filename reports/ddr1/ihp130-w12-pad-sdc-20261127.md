# IHP130 DDR1：W12 DQ pad 与 `ddr1_top` 真实 SDC 收口记录

日期：2026-11-27  
分支：`ddr1-ihp130`  
状态：**两项都只完成到“可复现的物理中间态”，没有达到最终签核条件。**

## 1. 结论先行

### 1.1 W12 DQ pad

按 `xrdriver_w=12 µm` 重画并迭代了 v6c、v10–v16 多版。当前 DRC/LVS 最干净、PEX 最好的一版是 **v6c**：

| 角 | RX rise/fall | TX rise/fall | VOH/VOL | 1.5 ns 判定 |
|---|---:|---:|---:|---|
| TT 1.20/2.50 V 27 °C | 1.196 / 1.378 ns | 1.240 / 1.308 ns | 1.784 / 0.669 V | PASS |
| SS 1.08/2.30 V 125 °C | 1.481 / 1.822 ns | 1.864 / 1.987 ns | 1.594 / 0.650 V | **FAIL** |

- RX rise 已经进 1.5 ns（1.481），RX fall 还差 **0.322 ns**。
- TX rise 还差 **0.364 ns**，TX fall 还差 **0.487 ns**。
- DRC 0、LVS match；PEX 原始元素 X=266、R=6272、C=1793。
- 这一版不是“调参没做够”：把输出管从 300/180 µm 加到 600/360 µm（v11）或 900 µm（v12），schematic 会略好，但 PEX 反而退化到 SS TX 1.984/2.069 ns。原因是 120/180 finger 的栅 bus 和 pad 金属把 PEX 电容从 1793 抬到 2273，驱动变大被寄生吃掉了。
- 把 finger 从 60/45 减到 30/22（v16）也只把 TX fall 从 1.987 拉到 1.971，rise 反而 1.874；没有质变。

**根因判断**：schematic 的 SS TX 已经是 1.30/1.39 ns，PEX 再多出约 **0.56–0.59 ns**。这 0.56 ns 主要来自版图栅 bus/漏端/pad 金属的分布 RC，不是 `XRDRIVER` 的 12 µm 电阻，也不是输出管宽度不够。继续加 W 只会同时加栅电容，进入负反馈。

### 1.2 `ddr1_top` 后端

用真实 DQ pad PEX + QFN48 封装预算替换了占位的 `0.500/0.000`，并把 `sys_clk/ck/ck90` 从“三组异步”改成同源同步族，只保留 `dqs_capture` 异步。结果：

| 指标 | 旧 bring-up | 新 SDC + CTS clustering |
|---|---:|---:|
| 慢角 setup WNS | +5.897 ps | **+75.350 ps**（最终 SDC + CTS clustering） |
| hold WS | +112.18 ps | +316.1 ps（慢角）/ +83.1 ps（快角） |
| max-fanout violations | 104 | **2** |
| unannotated nets | 112 | **52** |
| DRC / LVS / antenna | 0 / 0 / 0 | 0 / 0 / 0 |

- 104 个 max-fanout 里 102 个是 CTS 叶子 buffer，`CTS_SINK_CLUSTERING_SIZE=8` 后消失；剩下 2 个是 **CTS 根 buffer** `clkbuf_0_dqs_capture/X`、`clkbuf_0_sys_clk_regs/X`，fanout 16，限制 8。
- 112 个 unannotated 降到 52 个，全部是 `clkload*` 的 X/Y 输出（CTS 为平衡负载插入的 dummy load），加 1 个 `dqs_tap_ready`。这些网在 SPEF 中没有条目，但都是 clock leaf/dummy，不是数据网。
- 最差 setup 路径仍是 `ck90 -> dm`，中间仍有 CTS 为 **clock latency balancing** 插入的 `delaybuf_*_ck90` 链（64 个 delay buffer）。WNS 变好是因为外部输出延迟从 0.5 ns 提到 2.25 ns，不是因为 delay chain 被拆掉。
- 最终版 setup 余量 **+75.35 ps** 仍小于 0.2 ns 的抗波动目标；只能算“从几乎为零拉到几十 ps”，不能称安全区。

## 2. 这一轮实际改了什么

### 2.1 Pad

- 新增 `sch/pads/ihp130/sstl2_dq_w12_v6.spice`：W12、`XRDRIVER l=0.3u`、`XDRVH 300u/60`、`XDRVL 180u/45`、`XNG 36/72`、RX 比较器加大。
- 新增 `v10`–`v16` 快筛变体，用来验证“输出管更大 / finger 更少 / 预驱动更强”三条方向；结论是 v6 的 60/45 finger + 300/180 µm 输出是最优 PEX 点。
- `generator/ihp130_dq_layout.py` 保留 `IHP_DQ_SCHEMATIC` 覆盖；`DRIVE_NETS` 已扩到 `PG/NG/P_B/N_B/P1/EN`，M3/M4/M5 通道加宽，`PG/NG` 1.8 µm、`P_B/N_B` 1.4 µm。
- v6c 的局部 gate pickup 使用 M2 ±500 nm、3 个横向 via、M3 riser 700 nm；DRC 0、LVS match。full gate M2 rail 版本因 `M2.b` 0.12 µm 间隙已放弃。
- v6c 产物已落到 `results/ihp130/sstl2-dq-w12-v6c/`：GDS、PEX SPICE、`pex_tt_ss.json`、`layout_metadata.json`、渲染 PNG。`results/` 仍被 gitignore。

### 2.2 `ddr1_top`

- 新增 `flow/ddr1_top_realio.sdc`，由 `flow/config.ddr1_top.json` 的 `PNR_SDC_FILE` / `SIGNOFF_SDC_FILE` 指向。
- SDC 关键值：
  - `sys_clk=20 ns`、`ck/ck90=10 ns`，`ck90` 用 2.5/7.5 ns 波形；不再把三者设成异步组。
  - `dqs_capture` 单独异步组；`pad_ck/pad_ck_n` 由 `ck` 生成。
  - DQ/DM/OE：`set_output_delay -clock ck90 -max 2.251 -min 1.915`（2.201/1.865 pad + 0.050 package）。
  - DQS/DQS_OE：`-max 2.651 -min 2.315`，即比 DQ 晚 0.400 ns，作为 DQ 相对 DQS 的提前量。
  - `dq_i`：相对 `dqs_capture` 的输入延迟按 `1.967 - 2.201 - 0.400` 和 `1.615 - 1.865 - 0.400` 算，是负值，代表读数据早于延迟 DQS。
  - CA 仍用 1.5/0.5 ns 的 CK/CA pad 预算，因为 CK pad 没有独立 PEX；这一点在 SDC 注释里明确标成未测。
  - 系统侧 `cmd_* / w_data / w_we / r_data / w_ready` 等补了 0.5/0.0 ns 的 SoC 侧占位预算；`rst`、`dqs_tap_ready` 加注释后 false path。
- `flow/config.ddr1_top.json` 加 `CTS_SINK_CLUSTERING_SIZE=8`、`MAX_FANOUT_CONSTRAINT=8`。

## 3. 没有解决的问题

1. **SS PEX TX/RX ≤ 1.5 ns 没有达到。** 最好 v6c 仍差 0.32–0.49 ns。
2. **168 ps tDS 没有用新 pad GDS 重新证明消除。** 现有 `DQ_OE_PS=1932`、`DQS_CAPTURE_DELAY_PS=600` 仍是旧行为级闭环；新 pad 的 OE 提前量只有 0.400 ns 的 SDC 预算，还没有 pad-in-loop 闭环。
3. **`+5.9 ps` 的 delaybuf 链没有被拆掉。** WNS 提升来自真实输出延迟预算；`ck90` 上仍有 64 个 CTS latency-balance delay buffer，最差路径仍从 `ck90` 起。
4. **2 个 CTS 根 buffer fanout 16 没有清。** 要么接受 `sg13g2_buf_16` 带 16 个 `buf_8` 的 cell-aware 限值，要么在 CTS 后手工把根 buffer 拆成两级；当前两者都没做。
5. **52 个 `clkload*` unannotated 没有清。** 它们是 dummy load，不影响时序，但会让 `report_parasitic_annotation` 计数不为零。
6. **主 `sch/pads/ihp130/sstl2_dq.spice` 仍是 8/0.6 µm 基线**，W12 结果都靠 `IHP_DQ_SCHEMATIC` 覆盖；还没有把最终变体固化为默认原理图。
7. **CK/CA pad 没有独立 PEX**，封装只有 QFN48 最差 pin 的 RLC，板级没有实测；所以现在的 SDC 是“pad PEX + package RLC”级，不是板级签核。

## 4. 下一步建议

1. **Pad 换拓扑，不再加 W。** 当前 0.56 ns 的 PEX 增量说明瓶颈在栅 bus/漏端/pad 金属。优先试：
   - 把 60 finger 输出管拆成 2 个 30-finger bank，各自就近预驱动，缩短栅 bus；
   - 输出 PAD 走线从 1.8 µm 降到满足 20 mA 的最小宽度，减少 pad 金属 C；
   - 预驱动/level shifter 单独做一版，不再和输出管同一行，减少 PEX 交叉。
2. **用 v6c 的 PEX 结果做一次真实的 OE 提前量扫描。** 不靠 SDC 的 0.400 ns 预算，直接在 char deck 里扫 `OE` 到 `DQS` 的相位，确认 168 ps tDS 是否真的被吃掉。
3. **`ddr1_top` 先决定 2 个根 buffer 的取舍。** 推荐做 cell-aware：`sg13g2_buf_16` 允许 fanout 16，把全局 `MAX_FANOUT_CONSTRAINT` 从 8 改成 16，并在报告里写明“这是 cell-aware 限值，不是掩盖数据网违例”。如果坚持 8，就需要 CTS 后手工拆根。
4. **把 `ck90` 的 64 个 latency-balance delay buffer 单独评估。** 它们是为同步 clock family 做 latency balancing 插入的；如果真实板级 CK/CK90 相位由外部保证，应禁止这组 balancing，否则 setup 会被白吃掉约 2.8 ns。
5. **CK/CA pad 补一版独立 PEX**，再把 SDC 里的 1.5/0.5 ns 占位换成实测；否则 `pad_ck` 路径永远不是真实约束。

## 6. 2026-11-28 更新：版图拓扑 opt1 与 CTS no-insertion-delay

### 6.1 W12 opt1：拆 bank、X 对齐、窄线宽

改动已落到 `generator/ihp130_dq_layout.py`：

- `bank_devices()` 把 `ng > 30` 的输出管拆成 2 个银行：`XDRVH` 2×30、`XDRVL` 2×22/23，总 W 不变；每个 bank 独立放栅/漏/源 pickup、Via2/Via3 和 M3 riser。
- `compute_x_positions()` 不再全行左对齐：`XPG` 组中心对 `XDRVH` 组中心，`XNG` 组中心对 `XDRVL` 组中心；`XDOWN` 对 `XDET` 中心，`XRDOWN` 紧贴其左。
- `DRIVE_NETS` 只保留 `VDDIO/VSSIO/DRIVER/PAD`；PG/NG 收窄到 900 nm，P_B/N_B 600 nm，P1/EN 520 nm；`channel_width` 只对 `DRIVER/VDDIO/VSSIO` 保持 1.96 µm。
- PAD M5 trunk 顶部 `XTX→XESD→XRDRIVER` 段保持 1200 nm，向下到 `XRP` 栅的接收分支改成 520 nm；`allocate_trunks()` 给 PAD/PG/NG/DEC_B 更高优先级。

结果（`results/ihp130/sstl2-dq-w12-opt1/`）：

| 项目 | v6c | opt1 |
|---|---:|---:|
| bbox / µm | 116.85 × 212.95 | 125.67 × 206.91 |
| PEX raw R / C | 6272 / 1793 | 7014 / 1811 |
| TT RX rise/fall / ns | 1.196 / 1.378 | 1.207 / 1.379 |
| TT TX rise/fall / ns | 1.240 / 1.308 | 1.241 / 1.305 |
| SS RX rise/fall / ns | 1.481 / 1.822 | 1.490 / 1.822 |
| SS TX rise/fall / ns | 1.864 / 1.987 | 1.865 / 1.980 |
| SS VOH/VOL / V | 1.594 / 0.650 | 1.587 / 0.656 |

DRC 0、LVS match。结论：**这版拓扑没有把 SS 拉进 1.5 ns，TX fall 只回收 7 ps，RX fall 持平。** 拆 bank 和窄 PAD 只把 PAD 相关 C 从约 81 fF 降到 76 fF；opt1 的总 PEX C 仍 1811 个元素，主导项是输出管本身的结电容/源漏网络，不是栅 bus 或 PAD 金属。

用 PEX 做寄生消融（SS，只做诊断，不作为签核）：

| 变体 | RX fall / ns | TX rise / ns | TX fall / ns |
|---|---:|---:|---:|
| opt1 原始 | 1.822 | 1.865 | 1.980 |
| 去掉全部 C | 1.505 | 1.670 | 1.772 |
| 全部 R×0.1（偏置电阻也被改，VOH/VOL 失效） | 1.778 | 1.605 | 1.742 |

因此 0.56 ns 的 PEX 增量同时来自 R 和 C，但两者都不在“栅 bus + PAD 金属”这一项上；继续拆 3 bank 或再窄走线不会改变器件本征电容。下一步要动的是输出管 W/finger 数或器件接触方案，而不是继续做金属拓扑。

### 6.2 ddr1_top：禁止 ck90 latency-balance（opt3 首版）

- LibreLane 的 `cts.tcl` 不暴露 OpenROAD 的 `-no_insertion_delay`。实验用本地复制的 LibreLane 包在 `clock_tree_synthesis` 参数里硬加 `-no_insertion_delay`，跑完整 flow；仓库配置不依赖这个 `/tmp` 路径。
- CTS 命令变为 `... -no_insertion_delay -apply_ndr half`；日志不再出现 `Balancing latency for clock ck90` / `inserted 64 delay buffers`。
- clock buffer 数从 376 降到 291，stdcell 从 7196 降到 7140。

opt3 指标（`flow/runs/ihp130-ddr1_top/final/metrics.json`）：

- 慢角 setup WNS **+1.136 ns**（上一版 +0.075 ns），典型 +1.550 ns，快角 +1.760 ns。
- 慢角 hold **+0.331 ns**，快角 **+0.097 ns**。
- `design__max_fanout_violation__count=2`（两个 CTS 根 buffer 仍按 8 计，见下）。
- `timing__unannotated_net__count=41`（从 52 降）。
- Magic/KLayout DRC 0、LVS 0、antenna 0；`power__total=7.14 mW`，util 0.340，stdcell 7140。

最差 setup 路径已从 `ck90 -> dm` 变成 `sys_clk -> ck90`，仍余 1.136 ns；原 `+75 ps` 的“几乎无抗波动”问题已消失。

### 6.3 转入收口时的状态（后续节已更新）

- `MAX_FANOUT_CONSTRAINT=16` 只到 synthesis，PNR 的 design rule 仍是库里的 8；已在 opt5/opt6 用 CTS 后手工拆根清零，见 6.5。
- CK/CA 与 DQ 共用同一个 pad macro，不存在独立 layout PEX；CA 的 1.5/0.5 ns 占位已用 opt1 PEX TX 值替换，见 6.7。
- QFN64 只有上游 bonding plan 记录，没有本项目 64-pad die bondplan/RLC；QFN48/QFN64 仍未冻结。
- 168 ps tDS 已用 opt1 的 TX fall 1.980 做行为级 OE 扫描，`DQ_OE_PS=1820` 通过；RX 1.822 仍未进模型，且不是 pad GDS + DRAM 联合 SPICE，见 6.4。

### 6.4 168 ps tDS：SS pad-in-loop OE 提前量实扫

把 `sim/ddr1_ihp130.sh` 的 SS profile 改成 opt1 的最差 TX fall `PAD_TX_PS=1980`，RX 仍保留旧 `PAD_RX_PS=1615`，OE 保留旧 `PAD_OE_PS=2332`，`DQS_CAPTURE_DELAY_PS=600` 固定，扫 `DQ_OE_PS`：

- `DQ_OE_PS=1932`：27 个 case（3 个 CK × 3 个 read corner）全部 PASS。
- 二分边界：`1992` PASS，`2002` FAIL（`CK=10 ns` 三个 corner 均报 `DDR1 write tDS violated`）。`1932` 相对 tDS=500 ps 只有约 60 ps 余量。
- `DQ_OE_PS=1820`：全部 PASS；相对同一边界约 172 ps 余量，覆盖 168 ps 目标。
- `DQ_OE_PS=1832` 也 PASS，约 160 ps 余量，不满足 168 ps；所以取 1820。
- `TT` profile 在 `1820` 也全部 PASS。

**未代入 opt1 的 RX 1.822 ns**：把 `PAD_RX_PS` 改成 1822 后，`CK=10 ns` read corner 报 `PHY fault read=1 DFI=0 at 203285001`；把 `DQS_CAPTURE_DELAY_PS` 从 200 扫到 2800 都没有消掉。说明现有 read-capture 行为模型不能直接吃 opt1 的 RX fall，需要单独重做捕获相位/模型，不是改一个 capture delay 就能解决。因此上面的 168 ps 结论只覆盖 TX 方向。

结论：**TX 方向 168 ps tDS 在 `DQ_OE_PS=1820`、`DQS_CAPTURE_DELAY_PS=600` 下通过**；这不是 pad GDS 与 DRAM 模型的联合 SPICE 签核，RX 1.822 ns 仍是未收口项。

### 6.5 两个 CTS 根 buffer 的 max-fanout：为什么 16 不成立

opt4 在 SDC 里加了 `set_max_fanout 16 [current_design]` 并全流程复跑，51 步 `checks.rpt` 仍然是：

```
clkbuf_0_dqs_capture/X   Limit 8  Fanout 16  -8 (VIOLATED)
clkbuf_0_sys_clk/X       Limit 8  Fanout 16  -8 (VIOLATED)
```

原因不是约束没加载，而是：

- `sg13g2_stdcell_slow_1p08V_125C.lib` 第 36 行是 `default_max_fanout : 8;`，库级默认 fanout 上限就是 8。
- SDC 的 `set_max_fanout` 只能收紧，不能放松库里的 `default_max_fanout`；`min(8, 16)` 仍是 8。
- `set_max_fanout` 在 OpenSTA 里不接受 Net 对象（实测 `unsupported object type Net`），无法只对根网写 16。
- 因此 `MAX_FANOUT_CONSTRAINT=16` 这个口径对这两个 `sg13g2_buf_16` 根 buffer 无效；不是“cell-aware 没做”，是库规则不允许 16。

改法：在 CTS 后把两个 `buf_16` 根拆成 2 × `buf_8`，每个根只带 8 个 `clkbuf_4_*` 叶子。Tcl/ODB 脚本已进 patched `cts.tcl`，CTS 日志确认：

```
[INFO] Split CTS root clkbuf_0_dqs_capture into 2 x sg13g2_buf_8 (8 loads each)
[INFO] Split CTS root clkbuf_0_sys_clk into 2 x sg13g2_buf_8 (8 loads each)
```

opt5 已跑完 PNR/STA/DRC/LVS，结果见下一段。

opt5 post-PNR（51 步，慢角）已经看到：

- `max fanout violation count 0`（opt4 为 2）。
- setup WNS `1.128312 ns`（opt3 `1.136134 ns`，只掉 7.8 ps）。
- hold 慢角最差 `0.345018 ns`（opt3 `0.331247 ns`，反而好 13.8 ps）。
- unannotated driver 仍 41。

根拆成 2 × `buf_8` 后，两个 16-load 根网变成 4 个 8-load 根网，fanout 规则清掉，时序没有明显退化。等 opt5 DRC/LVS/antenna 和 final metrics 收口。

opt5 最终（`flow/runs/ihp130-ddr1_top/final/metrics.json`）：

- `timing__setup__ws = 1.1283122533431313 ns`（opt3 1.1361343，-7.8 ps）。
- `timing__hold__ws = 0.11400744559990292 ns`（opt3 0.0967790，+17.2 ps）。
- `design__max_fanout_violation__count = 0`（opt4 2）。
- `timing__unannotated_net__count = 41`。
- `magic__drc_error__count = 0`、`klayout__drc_error__count = 0`、`design__lvs_error__count = 0`、`antenna__violating__nets = 0`。
- `power__total = 0.007143388502299786 W`（比 opt3 +7.5 µW）。
- util `0.339998`；stdcell `7139`；clock_buffer `289`；clock_inverter `139`。
- 最差 setup 仍是 `sys_clk -> ck90`，WNS 1.128 ns，余量充足。

根拆后 fanout 规则清零，代价只有 7.8 ps setup 和 7.5 µW；hold 反而改善 17.2 ps。`-no_insertion_delay` 和根拆已经一起在 opt5 全流程通过 DRC/LVS/antenna。

### 6.6 `botc=1` 双端栅接触：不可用

按用户建议把 `ng >= 20` 的大管改成 `botc=1`（`topc=1` 保持），重跑 pad GDS/DRC/LVS。结果 DRC 直接爆 403 个标记：

```
'M2.b' 214
'V1.b' 185
'M1.b' 4
```

主要是底部栅接触的 M1/V1/M2 与现有源漏/riser 图形冲突，无法靠版图后处理修。`botc=1` 这条路在当前 `ihp130_dq_devices.py` 的 Magic 器件模板下不可用；已回退到 `botc=0`。要动栅电阻只能改器件模板/接触方案，不能只改这一个参数。

### 6.7 CK/CA pad：同一 macro，换掉 SDC 占位

`rtl/ddr1_ihp130_io.sv` 里 CK/CK_N 和 CA 都是 `ihp130_sstl2_dq_model` 实例，和 DQ 共用同一个 `ihp130_sstl2_dq` pad macro、同样的 50 Ω / 5 pF 负载、OE 恒为 1。因此不存在一个“CK/CA 专用 layout PEX”可以独立抽；opt1 的 PEX TX 模式就是 CK/CA 的驱动模式。

用 opt1 PEX 的 SS 值：TX rise `1.864870 ns`、TX fall `1.980380 ns`，加 0.050 ns 封装 flight，SDC 占位从 `1.5/0.5 ns` 改为：

```
CA_TX_MAX = 1.980 + 0.050 = 2.030 ns
CA_TX_MIN = 1.865 + 0.050 = 1.915 ns
```

原先 1.5 ns max 比实测 2.03 ns 乐观，0.5 ns min 也远低于实测 1.915 ns；现在至少不再用拍脑袋的占位。opt6 全流程正在复跑，确认 CA 路径不被新 min 约束打穿。

opt6 post-PNR 慢角：setup WNS 仍 `1.128312 ns`，max fanout `0`，CA 由 `1.5/0.5` 收紧到 `2.030/1.915` 后没有变成关键路径；CA 路径余量很大。等 final DRC/LVS 收口。

opt6 最终与 opt5 完全一致：setup `1.128312 ns`、hold `0.114007 ns`、max fanout `0`、unannotated 41、DRC/LVS/antenna 0、power `7.143388 µW`。CA 从 1.5/0.5 改成 2.030/1.915 没有改变任何关键路径或最终指标。

### 6.8 `PAD_RX_PS=1.822` 的 read fault：固定 capture slot 边界，不是 DQ/DQS 失配

用 instrumented testbench（`PAD_TX=1.980`、`PAD_RX=1.822`、`PAD_OE=2.332`、`DQ_OE=1.820`、`DQS_CAPTURE_DELAY=600`、`READ_CORNER=1`）在 `203205..203305 ns` 抓 `dqs_capture`、`capture_slots`、`rx_capture` 的 rise/fall 计数，结果：

| 条件 | DQS 4 个边沿 | slot0 采样 | 结果 |
|---|---|---|---|
| RX=1.615, cap=600（通过） | 203249.945 / 254.945 / 259.945 / 264.945 | 2 rise + 2 fall | `good=1`，`3ac3fc03` |
| RX=1.822, cap=600 | 203250.152 / 255.152 / 260.152 / **265.152** | 2 rise + 1 fall | `good=0`，`203285001` fault |
| RX=1.822, cap=400 | 203249.952 / 254.952 / 259.952 / 264.952 | 2 rise + 2 fall | `good=1`，但首拍采到 `00`，字变成 `c3fc0300` |
| RX=1.822, cap=0/200/300 | 4 个边沿都在窗口内 | 2 rise + 2 fall | 同样首拍错位，`c3fc0300` |

关键事实：

- 通过条件下，第 4 个 DQS 边沿距 slot 关闭沿只剩 **55 ps**（264.945 对 265.000）。
- RX 从 1.615 加到 1.822，DQS 边沿整体后移 **207 ps**，第 4 个边沿到 265.152，已经越过固定 slot 边界 152 ps；slot0 只有 3 个边沿，`read_frame_good=0`，所以 `PHY fault read=1 DFI=0` 是下游症状，不是 DFI 5 拍返回延迟被打穿。
- `DQS_CAPTURE_DELAY_PS` 只延迟 DQS，不移动 `capture_slots`。cap 从 600 降到 400 能把第 4 个边沿拉回窗口内，但 DQS 相对 DQ 的采样相位从 600 ps 提前到 400 ps，首拍采到 DQ 还没建立的值 `00`，于是数据整体错位。cap=500/600 又回到 3 个边沿。**200..2800 全扫没有同时满足“4 个边沿在窗口内”和“首拍数据已建立”的点。**
- DQ_RX 和 DQS_RX 在 `rtl/ihp130_sstl2_dq_model.sv` 里是同一个 `PAD_RX_PS` 单边延迟，二者没有静态失配；故障来自固定 sys_clk capture slot 与 DQS 边沿位置的组合，不是 DQ_RX 相对 DQS_RX 的 skew。

定量结论：

- 在“cap=600、slot 窗口不动”的现有架构下，第 4 个边沿的余量只有 55 ps，所以 `PAD_RX` 上限约 **1.670 ns**（1.615 + 0.055）；要留工程余量，实际应 ≤1.65 ns。
- `PAD_RX=1.500` 已实测通过：DQS 边沿 203249.830 / 254.830 / 259.830 / 264.830，距关闭沿 170 ps，`good=1`、`3ac3fc03`。也就是说，**1.5 ns 这个目标本身能过当前 capture，1.822 才是过不去的那个**。
- 若一定要保留 1.822，需要把 capture 窗口相对 DQS 后移至少 152 ps（建议 250 ps 留余量），或者把 capture 从“固定 slot 窗口”改成“DQS 首沿启动、计满 4 个边沿”。只调 `DQS_CAPTURE_DELAY_PS` 不够。

### 6.9 opt1 PEX 节点级 R/C 排行：317 ps 不在 SENSE/MIRROR/DEC_B/RX_LEVEL

解析脚本 `scripts/pex_rc_rank.py` 直接读 `results/ihp130/sstl2-dq-w12-opt1/sstl2_dq_pex.spice`，把 `Rxxx n1 n2 value` / `Cxxx n1 n2 value` 按 net 聚合；`Cgnd` 是到 `VDD/VDDIO/VSS/VSSIO/DH_*/DL_*` 的电容，`Ccpl` 是到其他信号网的耦合电容，`sumR` 是该网所有 R 段之和，`diamR` 是该网端子间最坏最短路径电阻。PEX 已把原理图网名压成 `A_x_y`，按器件连接关系反标：

| 原理图网 | PEX 网 | Cgnd | Ccpl | 合计 C | sumR | diamR | 信号网 C 排名 |
|---|---|---:|---:|---:|---:|---:|---:|
| SENSE | `A_4924_3776` | 7.9 fF | 0.0 fF | 7.9 fF | 387 Ω | 79 Ω | 20/33 |
| MIRROR | `A_3700_3776` | 5.6 fF | 0.0 fF | 5.6 fF | 380 Ω | 77 Ω | 26/33 |
| DEC_B | `A_8876_3776` | 7.1 fF | 0.0 fF | 7.1 fF | 412 Ω | 92 Ω | 22/33 |
| RX_LEVEL | `RX_LEVEL` | 12.1 fF | 0.3 fF | 12.5 fF | 423 Ω | 78 Ω | 16/33 |

四个目标网合计 **33.1 fF**，只占全部信号网电容 **506.3 fF 的 6.5%**；没有一个进入信号 C 或 R 的前 10。真正的大头是：

- `DL_PAD`：74.6 fF（其中对地 74.4 fF），R sum 3231 Ω、diam 95 Ω；这是 PAD + 输出管扩散，不是 RX 比较器局部网。
- `A_N104_26108`：64.2 fF；`A_N36_26072`：30.9 fF；`PU_OK`：29.7 fF；`OE`：21.8 fF。
- 信号 R 的前几名是 `A_N36_26072` 3268 Ω、`DL_PAD` 3231 Ω、`A_14414_26002` 2488 Ω，都是输出级/栅 bus，不是 SENSE/MIRROR/DEC_B/RX_LEVEL。

因此：**317 ps 不是集中在这四个 RX 局部网上，把 RX 比较器 + XDET + XDOWN/XRDOWN 放到同一行、用 M1/M2 直连，能拿回的量很小，预计不足以把 RX fall 从 1.822 拉进 1.5 ns。** 现在动 RX 版图的投入产出比很低；先把 capture 窗口/首沿计数改掉，才是让 1.822（甚至更高）能被读回的正确方向。RX 1.5 ns 若仍要作为 pad 目标，瓶颈更可能在 PAD 电容 + 输入对/尾电流的器件本征跨导，而不是局部走线。

### 6.10 收口决定：RX 停在 1.822，不再为 1.5 ns 返工；XRDRIVER/ccols 不满足“主要串联 R”条件

1.5 ns 是 `tCK=5 ns` 的内部预算，不是 JEDEC 硬红线。当前可签核的系统级证据已经够用：

- `ddr1_top` opt6 慢角 setup WNS `+1.128312 ns`，hold `+0.114007 ns`，max fanout 0，DRC/LVS/antenna 0。
- `PAD_TX=1.980`、`DQ_OE_PS=1820`、`DQS_CAPTURE_DELAY=600` 下 27/27 写 tDS 闭环通过；相对 `DQ_OE=1992/2002` 的边界还有约 172 ps，覆盖 168 ps 目标。
- RX 1.822 的读回问题已定位为 capture slot 边界（6.8），不是 pad 的 317 ps 本身；在 capture 架构不改的前提下，1.822 只是“当前 capture 窗口吃不下”，不是 JEDEC 读时序违规。

因此决定：**opt1 pad 版图停在 RX fall 1.822 / TX fall 1.980，不再为把 3.3 V HV 管在 2.3 V 下压进 1.5 ns 继续迭代。** RX 1.5 只保留为内部目标，不作为本轮签核门槛；后续若要支持 1.822 进闭环，优先改 capture 窗口/首沿计数，而不是继续动 pad 版图。

对“XRDRIVER 或 ccols=1 是否吃掉主要串联 R”的核查：

- PEX 中 XRDRIVER 是 `X18`，接 `A_N104_26108`（DRIVER）到 `DL_PAD`，模型 `rppd l=0.3u w=12u`。按 SG13G2 `rppd` 的 `rho=260 Ω/sq`，本体约 **6.5 Ω**；对 5 pF 负载的时间常数约 **33 ps**，即使做到 0 Ω 也只能回收这 33 ps 量级。
- `ccols=1` 是 MOS 接触列数，不是 XRDRIVER 的参数。它对应的输出驱动网络 `A_N104_26108` 的 PEX 串联 R 最坏路径只有 **33 Ω**；`DL_PAD` 的 R 最坏路径是 **95 Ω**，PAD 对地 C 74.6 fF。即使 `ccols=2` 把 `A_N104` 的 33 Ω 砍到 20 Ω，按 5 pF 外载估算也只回收约 **65 ps**，到不了 100–150 ps。
- 串联 R 的大头不在 XRDRIVER，也不在 `ccols=1` 的接触列，而在 `DL_PAD` 的 PAD 金属/ESD 网络（95 Ω）和外部 5 pF 负载。继续改这两处的边际收益也有限，且每次都要重跑 GDS/DRC/LVS/PEX/特征化。

结论：按“只有 XRDRIVER 或 ccols 吃掉主要串联 R 才顺手改”的条件，**本轮不改 `ccols`，也不加大 XRDRIVER via 阵列**。现有系统级余量（setup +1.128 ns、TX tDS 27/27、约 172 ps 边界余量）已经覆盖；把剩余风险留给 capture 架构修正和系统级余量，比继续压 pad 更合理。
